# سفارش‌گیری در تلگرام

مشتری از چت بات، محصول را انتخاب می‌کند، تعداد و آدرس می‌دهد، لینک پرداخت می‌گیرد و
سفارش می‌گذارد. فروشنده اعلان می‌گیرد و در پنل وضعیت را جلو می‌برد.

> **این صفحه به `docs/TELEGRAM.md` وابسته است.** اگر بات هنوز وصل نیست، اول آن را
> راه بیندازید.

---

## ۰. یک‌بار بعد از آپدیت: webhook را دوباره ثبت کنید

دکمه‌های انتخاب محصول و مراحل سفارش با `callback_query` کار می‌کنند. اگر webhook را
قبل از این نسخه ثبت کرده‌اید، تلگرام کلیک دکمه را برای سرور **نمی‌فرستد** و هیچ
خطایی هم دیده نمی‌شود.

**پنل → تنظیمات → اتصال به تلگرام** → دکمه‌ی «ثبت webhook از سرور».
کارت پنل خودش این حالت را تشخیص می‌دهد و می‌نویسد: «webhook بدون callback_query
ثبت شده، پس دکمه‌ها کار نمی‌کنند».

## ۱. تجربه‌ی مشتری

```
مشتری: این مانتو چنده؟
بات:   «این مانتو چنده؟» به بیش از یک محصول می‌خورد.
       منظورتان کدام است؟ یکی را از دکمه‌های زیر انتخاب کنید:

       • مانتو کتان · از ۶۴۰٬۰۰۰ تومان · ۱ سایز/رنگ موجود
         کد: A1B2C3
       • مانتو ابریشمی · از ۱٬۲۰۰٬۰۰۰ تومان · ۱ سایز/رنگ موجود
         کد: D4E5F6
       یا نام دقیق محصول، یا کد آن را بفرستید.
       [ مانتو کتان ] [ مانتو ابریشمی ]
```

با انتخاب محصول:

```
بات: مانتو کتان
     موجودی و قیمت:
     • سایز ۳۸، رنگ کرم: ۶۴۰٬۰۰۰ تومان — ۳ عدد موجود
     کد محصول: A1B2C3
     [ 🛒 ثبت سفارش · سایز ۳۸، رنگ کرم ]
```

و بعد مراحل سفارش، هر کدام با دکمه‌ی لغو:

| مرحله | پرسش | ورودی |
|---|---|---|
| ۱ | چند عدد می‌خواهید؟ | دکمه ۱ تا ۵ یا عدد تایپی |
| ۲ | نام و نام خانوادگی گیرنده | متن، یا دکمه‌ی «همان نام تلگرام» |
| ۳ | شماره‌ی موبایل | `۰۹۱۲…`، `+98912…` و `912…` همه قبول است |
| ۴ | نشانی کامل پست | متن (حداقل ۱۰ کاراکتر) |
| ۵ | پیش‌فاکتور | دکمه‌ی «تأیید و دریافت لینک پرداخت» |
| ۶ | لینک پرداخت | دکمه‌ی لینک به درگاه |

## ۲. تشخیص محصول از پست فوروارد‌شده

مشتری می‌تواند پستی از کانال/چت دیگر را برای بات فوروارد کند:

- **با متن/زیرنویس**: همان متن به‌عنوان پرسش جستجو می‌شود و محصول(ها) پیدا می‌شوند.
- **بدون متن (فقط عکس)**: بات صریح می‌گوید «این پست متنی ندارد» و می‌خواهد نام یا
  کد محصول را بفرستد. عمداً حدس نمی‌زنیم؛ ما تصویر را نمی‌خوانیم.
- اگر پیام فورواردی باشد ولی محصولی پیدا نشود، بات می‌گوید از کدام منبع آمده و
  محصولش در کاتالوگ نیست، و همان را به فروشنده ارجاع می‌دهد.

## ۳. قواعدی که عمداً این‌طور است

| قاعده | چرا |
|---|---|
| ابهام → سؤال، نه حدس | اگر دو محصول با «کت» جور دربیاید، انتخاب با کاربر است. پاسخ غلط بدتر از سؤال است. |
| سایز/رنگ ناموجود → لیست گزینه‌های واقعی | «سایز XL» را با قیمت M جواب نمی‌دهیم. |
| موجودی **هنگام ساخت سفارش** رزرو می‌شود | اگر تا پرداخت صبر کنیم، دو مشتری یک عدد آخر را می‌خرند و یکی پول داده و جنس ندارد. |
| سفارش پرداخت‌نشده بعد از ۲۴ ساعت لغو و موجودی آزاد می‌شود | بدون cron هم درست می‌ماند؛ هنگام باز کردن صفحه‌ی سفارش‌ها اجرا می‌شود. |
| پرداخت فقط بعد از verify قطعی «پرداخت‌شده» می‌شود | `Status=OK` در بازگشت زرین‌پال یعنی «کاربر ادعا می‌کند پرداخت کرده»، نه اینکه پول رسیده. |
| تأیید/پرداخت دوباره، سفارش و اعلان تکراری نمی‌سازد | idempotent؛ مشتری ممکن است دوبار دکمه بزند. |
| عنوان و قیمت در لحظه‌ی ثبت کپی می‌شوند | تغییر نام/قیمت بعدی نباید سفارش قدیمی را عوض کند. |
| سقف ۱۰ عدد در هر سفارش | جلوگیری از اشتباه تایپی («۱۰۰» به‌جای «۱۰»). |

## ۴. پنل: صفحه‌ی سفارش‌ها

**پنل → سفارش‌ها** (`/app/orders`)

- چهار کارت بالا: در انتظار پرداخت، فروش ۲۴ ساعت گذشته، آماده‌ی ارسال، تحویل‌شده.
- فیلترهای وضعیت با شمارش.
- هر ردیف: کد سفارش، وضعیت، مشتری، اقلام، مبلغ، و دکمه‌ی گذار بعدی.
- «جزئیات»: اقلام، نشانی، تلفن (قابل تماس)، کد پیگیری پرداخت، دلیل لغو، و
  دانلود فایل متنی سفارش.

مسیر وضعیت:

```
AWAITING_PAYMENT ──(پرداخت)──> PAID ──> SHIPPED ──> COMPLETED
        │                        │          │
        └──────── CANCELLED ─────┴──────────┘   (موجودی برمی‌گردد)
```

دکمه‌ها فقط برای گذارهای مجاز نشان داده می‌شوند؛ API هم گذار نامجاز را با ۴۰۹ رد
می‌کند.

### API

| متد | مسیر | کار |
|---|---|---|
| `GET` | `/orders?status=&limit=` | لیست سفارش‌های فروشگاه |
| `GET` | `/orders/summary` | کارت‌های داشبورد |
| `GET` | `/orders/:id` | جزئیات |
| `POST` | `/orders/:id/status` | `{"status":"SHIPPED"}` یا `COMPLETED` یا `CANCELLED` |
| `GET` | `/payments/sandbox/:authority` | صفحه‌ی درگاه آزمایشی (عمومی) |
| `GET` | `/payments/zarinpal/callback` | بازگشت از زرین‌پال (عمومی) |

همه به فروشگاه خودِ توکن محدودند؛ شناسه‌ی سفارش فروشگاه دیگر → ۴۰۴.

## ۵. درگاه پرداخت

### حالت ۱ — آزمایشی (پیش‌فرض، بدون تنظیم)

اگر `ZARINPAL_MERCHANT_ID` خالی باشد، لینک پرداخت به صفحه‌ای روی همین سرویس می‌رود:

```
https://<آدرس-API>/payments/sandbox/<authority>
```

صفحه، خلاصه‌ی سفارش و دو دکمه دارد: «پرداخت موفق» و «انصراف». کل جریان سفارش،
اعلان فروشنده، لغو و برگشت موجودی **همین حالا** قابل تست است.

> ⚠️ حالت آزمایشی **هیچ پولی جابه‌جا نمی‌کند**. برای فروش واقعی باید مرچنت‌آیدی
> بگذارید. روی خود صفحه هم همین هشدار نوشته شده تا مشتری واقعی گمراه نشود.

### حالت ۲ — زرین‌پال (فروش واقعی)

1. از زرین‌پال مرچنت‌آیدی بگیرید.
2. Render → سرویس API → Environment → `ZARINPAL_MERCHANT_ID` = مرچنت‌آیدی.
3. `PUBLIC_API_URL` باید آدرس **https** و عمومی باشد (کارت بانکی بعد از پرداخت به
   `https://<آدرس-API>/payments/zarinpal/callback` برمی‌گردد).
4. دوباره دیپلوی کنید.

مبلغ: قیمت‌های پنل **تومان** هستند و زرین‌پال **ریال** می‌خواهد، پس درخواست با
`total × 10` فرستاده می‌شود.

اگر پرداخت بعد از لغو سفارش انجام شود (مشتری صفحه‌ی پرداخت را باز گذاشته)، بات به
فروشنده هشدار می‌دهد که این مبلغ باید مرجوع شود — به‌جای اینکه بی‌صدا نادیده گرفته
شود.

## ۶. متغیرهای محیطی

| متغیر | لازم؟ | کار |
|---|---|---|
| `PUBLIC_API_URL` | ✅ برای پرداخت | آدرس https سرویس API؛ لینک پرداخت و callback از این ساخته می‌شود |
| `ZARINPAL_MERCHANT_ID` | برای فروش واقعی | بدون آن، درگاه آزمایشی |
| `ZARINPAL_API_BASE` | فقط تست | پیش‌فرض `https://api.zarinpal.com` |
| `TELEGRAM_BOT_TOKEN` | ✅ | بات |
| `TELEGRAM_WEBHOOK_SECRET` | ✅ | سکرت webhook |

## ۷. عیب‌یابی

| نشانه | علت | کار |
|---|---|---|
| دکمه‌ها در بات کار نمی‌کنند | webhook بدون `callback_query` ثبت شده | پنل → تنظیمات → «ثبت webhook از سرور» |
| «فعلاً امکان ساخت لینک پرداخت نیست» | `PUBLIC_API_URL` ست نشده | آن را ست کنید و ری‌استارت |
| `سفارش ثبت نشد: موجودی این محصول کافی نیست` | دو مشتری هم‌زمان یا موجودی کهنه | موجودی را به‌روز کنید |
| صفحه‌ی درگاه ۴۰۴ می‌دهد | لینک قدیمی/نامعتبر | از `/orders` لینک تازه بگیرید |
| زرین‌پال خطای verify می‌دهد | مبلغ یا مرچنت‌آیدی ناهمخوان | لاگ سرویس: `zarinpal verify … code=`؛ مبلغ باید `total × 10` باشد |
| سفارش پرداخت‌شده ولی موجودی کم نشده | باید نشده باشد؛ رزرو **هنگام ساخت** است | تاریخچه‌ی موجودی را ببینید: `reason = order` |
| اعلان فروشنده نیامده | چت فروشنده وصل نیست | تنظیمات → «ساخت کد اتصال» |

## ۸. محدودیت‌های شناخته‌شده (صادقانه)

- **یک قلم در هر سفارش** از بات. سبد خرید چندقلوی وب وجود ندارد؛ چند قلم را
  فروشنده دستی اضافه می‌کند. API چند قلم را پشتیبانی می‌کند.
- **هزینه‌ی ارسال به مبلغ اضافه نمی‌شود**؛ سیاست ارسال فقط به‌صورت متن به مشتری
  گفته می‌شود. اگر لازم است، باید تعرفه در تنظیمات فروشگاه اضافه شود.
- **پرداخت فقط زرین‌پال**. آسان‌پرداخت/زیبال/idpay اضافه نشده‌اند؛ ساختار
  `PaymentsService` برای افزودنشان باز است.
- **بدون SMS**. اعلان‌ها فقط در تلگرام و پنل هستند.
- **بدون فاکتور PDF**. فقط فایل متنی از صفحه‌ی سفارش.
- **انقضای سفارش lazy است**: اگر هیچ‌کس صفحه‌ی سفارش‌ها را باز نکند، سفارش
  پرداخت‌نشده تا اولین بازدید بعدی لغو نمی‌شود. برای دقت کامل یک cron روزانه روی
  `/orders` بگذارید.
- **عکس محصول نمی‌خوانیم**؛ همان محدودیت `docs/TELEGRAM.md` بخش ۵.
