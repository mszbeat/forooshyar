# اتصال مدل زبانی به فروش‌یار

هدف این سند: وصل‌کردن یک مدل زبانی برای **فهمیدن و جواب‌دادن**، بدون آنکه
مدل هرگز بتواند قیمت، موجودی یا سیاست فروشگاه را از خودش بسازد.

> قاعده‌ی اصلی پروژه: مدل، «زبان‌فهم» است؛ **منبع حقیقت** دیتابیس فروشنده است.

---

## ۱. معماری در یک نگاه

```
پیام مشتری (تلگرام)
        │
        ▼
composeReply()  ← موتور قاعده‌محور (همیشه اول)
        │
        ├─ محصول/قیمت/موجودی تشخیص داده شد ──► پاسخ از کاتالوگ (بدون مدل)
        ├─ ارسال/پرداخت/ساعت/مرجوعی ─────────► پاسخ از تنظیمات فروشگاه (بدون مدل)
        ├─ سفارش در جریان (state machine) ──► هرگز به مدل نمی‌رود
        └─ «نفهمیدم» / «پیدا نشد» ──┐
                       ▼
            interpretWithAi()  ← فقط نیت را می‌خواند (JSON)
                       │
        ┌──────────────┼─────────────────┐
        ▼              ▼                 ▼
  محصول موجود     جست‌وجوی دوباره    موضوع فروشگاهی
  (قیمت واقعی)     با واژه‌های مدل    answerWithAi()
                       │
                       ▼
              guardAnswer()  ← نگهبان عدد و طول
                       │
             ┌─────────┴─────────┐
         قبول شد            رد شد
             │                  │
      پاسخ مدل          همان سؤال روشن‌کننده‌ی قاعده‌محور
```

سه لایه در کد:

| فایل | نقش |
| --- | --- |
| `backend/src/ai/ai.service.ts` | اتصال HTTP به هر درگاه سازگار با OpenAI، تایم‌اوت، قطع‌کننده‌ی مدار |
| `backend/src/ai/context.ts` | ساخت «بسته‌ی زمینه» (تنظیمات + کاتالوگ + تاریخچه) و نگهبان خروجی |
| `backend/src/ai/answer.ts` | تنها راه فراخوانی مدل: زمینه + نگهبان، یک‌جا |
| `backend/src/ai/interpret.ts` | تشخیص **نیت** پیام (JSON)، فقط از میان عنوان‌های واقعی کاتالوگ |
| `backend/src/ai/understand.ts` | تصمیم نهایی: قاعده‌محور، تطبیق محصول، یا پاسخ مدل |

### چرا «تشخیص نیت» جدا از «پاسخ‌دادن» است

جمله‌ی «می‌خوام قیمت کفش هاتون رو بدونم» در فروشگاهی با «کفش لوفر چرم مشکی»
باید همان کفش را نشان بدهد، ولی همان جمله وقتی کاتالوگ کفش ندارد باید صریح
بگوید «نیست». تطبیق حرف‌به‌حرف این دو را از هم جدا نمی‌کند؛ مدل می‌تواند — به
شرطی که اجازه نداشته باشد چیزی از خودش بسازد:

۱. مدل فقط از میان **عنوان‌های ارسال‌شده** انتخاب می‌کند؛ عنوانی که در کاتالوگ
   نباشد دور انداخته می‌شود (`interpret.ts`).
۲. قیمت و موجودی همیشه از دیتابیس می‌آید، نه از مدل.
۳. پاسخ روشن قاعده‌محور (قیمت یک محصول مشخص، ارسال، پرداخت، سفارش) هرگز با مدل
   جایگزین نمی‌شود — مدل در آن حالت حتی صدا زده نمی‌شود.
۴. اگر مدل هم محصولی پیدا نکند، پاسخ قاعده‌محور دست‌نخورده می‌ماند.

مسیرهای پنل: `GET /bot/ai` (وضعیت) و `POST /bot/preview` (پاسخ آزمایشی، همان
مسیری که مشتری می‌گیرد؛ فیلد `source` می‌گوید `rules` یا `ai`).

## ۲. راه‌اندازی در چهار قدم

### قدم ۱ — کلید و مدل را بگذارید

در `backend/.env` (و در Render → Environment):

```env
AI_ENABLED=true
AI_API_KEY=sk-...
AI_MODEL=gpt-4o-mini
AI_BASE_URL=https://api.openai.com/v1
```

`AI_BASE_URL` را می‌توانید عوض کنید؛ هر سرویسی که
`POST {base}/chat/completions` را با استاندارد OpenAI جواب بدهد کار می‌کند:

* `https://openrouter.ai/api/v1` (چند مدل با یک کلید)
* `https://api.groq.com/openai/v1` (سریع و ارزان)
* `http://127.0.0.1:8000/v1` (vLLM یا Ollama روی سرور خودتان — داده از کشور خارج نمی‌شود)

### قدم ۲ — سرور را دوباره بالا بیاورید

```bash
cd backend && npm run build && node dist/main.js
```

### قدم ۳ — چک کنید

```bash
# وضعیت
curl -s localhost:10000/bot/ai -H "Authorization: Bearer <TOKEN>"
# {"enabled":true,"ready":true,"model":"gpt-4o-mini","reason":""}

# پاسخ آزمایشی؛ source نشان می‌دهد مدل جواب داده یا قاعده‌ها
curl -s -X POST localhost:10000/bot/preview \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -d '{"message":"میشه بگی این مانتویی که گذاشتی چقدره؟"}'
```

### قدم ۴ — پایش

هر استفاده و هر رد شدن در دفتر گردش ثبت می‌شود:
`telegram.ai_answer` (پاسخ مدل پذیرفته شد) و `telegram.ai_skipped` (با دلیل:
`ai_disabled`، `no_answer`، `price_not_in_catalog:...`، `too_long`).

## ۳. چطور کلید و آدرس مدل را به من می‌دهید؟

سه راه دارید؛ هر سه به همین چهار متغیر ختم می‌شوند. **هیچ‌کدام لازم نیست کلید
را در چت بفرستید** — فقط در جای امن خودش بگذارید.

### راه ۱ (پیشنهاد برای لوکال) — فایل `.env` در بک‌اند

در WSL:

```bash
cd ~/Desktop/files/nestjs\ projects/forooshyar/backend
nano .env      # یا: code .env
```

این چهار خط را اضافه کنید:

```env
AI_ENABLED=true
AI_API_KEY=sk-...                       # کلید خودتان
AI_MODEL=gpt-4o-mini                    # یا هر مدلی که درگاهتان دارد
AI_BASE_URL=https://api.openai.com/v1   # آدرس درگاه
```

سپس:

```bash
npm run build && node dist/main.js
```

> `.env` در `.gitignore` است؛ با `git status` مطمئن شوید کلید در کامیت نمی‌رود.

### راه ۲ (پیشنهاد برای سرور) — Render → Environment

1. Render → سرویس بک‌اند → تب **Environment**.
2. چهار کلید بالا را با **Add Environment Variable** اضافه کنید (مقدار
   `AI_API_KEY` را Paste کنید؛ در لاگ‌ها نمایش داده نمی‌شود).
3. **Save Changes** — Render خودش سرویس را با مقادیر تازه ری‌استارت می‌کند.
4. اگر کلید را عوض کردید، بعد از Deploy از `/bot/ai` چک کنید `ready:true`
   باشد.

### راه ۳ — کدام درگاه؟ (`AI_BASE_URL` + `AI_MODEL`)

هر سرویسی که `POST {AI_BASE_URL}/chat/completions` را استاندارد OpenAI جواب
بدهد، بدون تغییر کد کار می‌کند:

| درگاه | `AI_BASE_URL` | نمونه‌ی `AI_MODEL` | کلید |
| --- | --- | --- | --- |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` | `sk-...` |
| OpenRouter | `https://openrouter.ai/api/v1` | `openai/gpt-4o-mini` | `sk-or-...` |
| OpenRouter (رایگان) | `https://openrouter.ai/api/v1` | `meta-llama/llama-3.3-70b-instruct:free` | `sk-or-...` |
| درگاه دلخواه (vLLM) | `http://IP:8000/v1` | نام مدل سروشده | معمولاً لازم نیست |
| Ollama روی سرور | `http://IP:11434/v1` | `qwen2.5:7b` | لازم نیست |

در پنل ادمین همین سه میزبان (OpenRouter، OpenAI، درگاه دلخواه) در یک بازشوی
«مسیر مدل» آمده‌اند. فهرست مدل‌های هر میزبان **زنده** خوانده می‌شود:

```http
GET /admin/ai/models?provider=openrouter[&baseUrl=…][&apiKey=…][&refresh=1]
```

سرور با همان کلید و آدرسی که برای گفتگو استفاده می‌شود `GET {baseUrl}/models`
را صدا می‌زند (کلید هرگز به مرورگر نمی‌رود)، مدل‌های غیرگفتگویی (embedding،
tts، تصویر) را حذف می‌کند و نتیجه را ۱۰ دقیقه کش می‌کند. اگر ارائه‌دهنده جواب
ندهد یا کلید نباشد، همان فهرست پیشنهادی کاتالوگ برمی‌گردد و پنل برچسب
«فهرست پیشنهادی» را نشان می‌دهد (به‌جای خطا). دکمه‌ی به‌روزرسانی کنار همان
برچسب، کش را دور می‌زند. نام مدل دلخواه را همیشه می‌توانید دستی بنویسید. دکمه‌ی **فقط رایگان** فهرست را به مدل‌های `:free` محدود می‌کند و
دکمه‌ی **آزمون اتصال با این مدل** همان‌جا (زیر انتخابگر مدل) یک درخواست واقعی
با مقدارهای ذخیره‌نشده می‌فرستد.

اگر درگاه locale خودتان است و کلید ندارد، مقدار `AI_API_KEY` را هر چیز
غیرخالی بگذارید (مثلاً `local`) — فقط برای این است که «وصل بودن» تشخیص داده
شود.

> ⚠️ اگر مدل را روی سرور خودتان می‌گذارید، آن سرور باید عمومی (https) باشد.
> تلگرام و Render نمی‌توانند به `127.0.0.1` ماشین شما وصل شوند.

### تأیید نهایی (۳۰ ثانیه)

```bash
curl -s localhost:10000/bot/ai -H "Authorization: Bearer <TOKEN>"
# انتظار: {"enabled":true,"ready":true,"model":"gpt-4o-mini","provider":"https://api.openai.com/v1","reason":""}
```

بعد در پنل → **آزمایشگاه دستیار**، یکی از این‌ها را بفرستید:
«گارانتی اصالت کالا دارید؟» — اگر پاسخ با برچسب **«پاسخ مدل زبانی»** آمد،
اتصال کامل است. اگر برچسب نبود، یعنی `source:"rules"`؛ دلیل رد شدن در
`telegram.ai_skipped` در دفتر گردش ثبت شده است.

### سرعت پاسخ

مدل روی مسیر بحرانی نمی‌ماند. `customerMessage` پاسخ آماده‌ی قاعده‌محور را
همیشه در دست دارد و مدل را با **بودجه‌ی زمانی** صدا می‌زند
(`AI_REPLY_BUDGET_MS`، پیش‌فرض ۴۰۰۰ms؛ لایه‌ی بازنویسی لحن حداکثر تا انتهای
همان بودجه). اگر مدل دیر کند، همان پاسخ آماده فوراً می‌رود و لحن مدل هم
به تعویق نمی‌افتد؛ نتیجه: مشتری هرگز بیش از چند ثانیه منتظر نمی‌ماند.

### اگر کلید را ندهید چه می‌شود؟

هیچ‌چیز نمی‌شکند: `AI_ENABLED` خالی می‌ماند، `enabled:false` برمی‌گردد و بات
همان‌طور که امروز کار می‌کند (کاتالوگ، قیمت، موجودی، ارسال، سفارش) جواب
می‌دهد. مدل فقط «افزودنی» است، نه پیش‌نیاز.

## ۴. بسته‌ی زمینه چه دارد و چرا؟

`buildFacts()` این متن را می‌سازد و همان را به مدل می‌دهد (و نگهبان با همان
مقایسه می‌کند):

```
## فروشگاه
نام: بوتیک باران
ارسال: پست پیشتاز، ۲ تا ۴ روز کاری.
پرداخت: پرداخت آنلاین یا کارت به کارت.
ساعت پاسخ‌دهی: هر روز ۹ تا ۲۳.
مرجوعی: تا ۷ روز.

## محصولات (۹ از ۱۰)
• [A1B2C3] مانتو کتان → سایز ۳۸ / رنگ کرم = ۶۴۰٬۰۰۰ تومان (۶ عدد) | سایز ۴۰ / رنگ مشکی = ۶۹۰٬۰۰۰ تومان (۲ عدد)
...
```

نکته‌های عمدی:

* **محصولات موجود اول** می‌آیند؛ اگر بودجه‌ی کاراکتر (پیش‌فرض ۵۵۰۰) تمام
  شود، محصولات ناموجود حذف می‌شوند نه قابل‌فروش‌ها.
* مدل صریح می‌بیند «۹ از ۱۰»؛ یعنی می‌داند فهرست کامل نیست و نمی‌تواند ادعای
  «همه‌ی محصولات» کند.
* تاریخچه فقط ۸ پیام آخر است (هزینه و تمرکز).
* کد محصول داخل بسته هست تا مشتری بتواند دقیق اشاره کند.

## ۵. چرا سفارش و پرداخت به مدل سپرده نمی‌شوند؟

`order-flow.ts` یک ماشین حالت است: مرحله‌ی سایز/رنگ → نام → تلفن → استان →
شهر → نشانی → کد پستی (اختیاری) → تأیید → لینک پرداخت. هر مرحله یا معتبر است
یا نیست؛ «تقریباً درست» وجود ندارد.

اگر مدل این مسیر را می‌گرفت:

1. **غیرقابل‌تکرار** می‌شد؛ یک پیام دو پالس متفاوت می‌گرفت.
2. **قابل‌حسابرسی نبود**؛ «چرا این سفارش با این آدرس ثبت شد؟» جواب نداشت.
3. **موجودی رزروشده گم می‌شد**؛ رزرو موجودی باید اتمیک باشد، نه نتیجه‌ی یک
   مکالمه‌ی آزاد.
4. **خطای پرهزینه** می‌داد؛ آدرس اشتباه یعنی مرسوله‌ی برگشتی.

جمع‌بندی: **مدل برای فهمیدن و توضیح‌دادن، ماشین حالت برای ثبت‌کردن.** این
تقسیم کار در کد رعایت شده است — مدل هیچ‌وقت در `continueOrder` صدا زده نمی‌شود.

## ۶. آزمون و امنیت

* `npm test` → `test/ai.test.ts`: ساخت زمینه، بودجه‌ی کاتالوگ، نگهبان قیمت،
  رفتار خاموش‌بودن مدل. هیچ تستی به شبکه نیاز ندارد.
* مدل بدون کلید = `enabled:false`؛ هیچ خطایی به کاربر نمی‌رسد.
* سه خطای پشت‌سرهم از ارائه‌دهنده → مدار ۲ دقیقه بسته می‌شود و بات با
  موتور قاعده‌محور ادامه می‌دهد (نه کندی، نه قطعی).
* داده‌ی حساس (توکن تلگرام، کلید درگاه) هرگز داخل پرامپت نمی‌رود؛ فقط نام و
  متن تنظیمات فروشگاه.

## ۷. کارهای بعدی (اختیاری)

1. **کلید هر فروشنده**: ستون `aiEnabled`/`aiKey` روی `Shop` و استفاده از کلید
   خود فروشنده (مدل مشترک، هزینه‌ی جدا).
2. **حافظه‌ی خلاصه**: هر ۲۰ پیام، یک خلاصه‌ی کوتاه بسازیم تا بسته‌ی زمینه
   کوچک بماند.
3. **ارزیابی**: مجموعه‌ای از ۵۰ سؤال واقعی مشتری + جواب درست، و سنجش نرخ
   پاسخ مدل در CI.
4. **حالت پیشنهاد**: مدل پاسخ را فقط «پیش‌نویس» کند و فروشنده در پنل تأیید
   کند (برای فروشگاه‌های محتاط).
