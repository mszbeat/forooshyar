# اتصال مدل زبانی به فروش‌یار

هدف این سند: وصل‌کردن یک مدل زبانی برای **فهمیدن و جواب‌دادن**، بدون آنکه
مدل هرگز بتواند قیمت، موجودی یا سیاست فروشگاه را از خودش بسازد.

> قاعده‌ی اصلی پروژه: مدل، «زبان‌فهم» است؛ **منبع حقیقت** دیتابیس فروشنده است.

---

## ۱. معماری در یک نگاه

```
پیام مشتری (تلگرام)
        │
        ▼
composeReply()  ← موتور قاعده‌محور (همیشه اول)
        │
        ├─ محصول/قیمت/موجودی تشخیص داده شد ──► پاسخ از کاتالوگ (بدون مدل)
        ├─ ارسال/پرداخت/ساعت/مرجوعی ─────────► پاسخ از تنظیمات فروشگاه (بدون مدل)
        ├─ سفارش در جریان (state machine) ──► هرگز به مدل نمی‌رود
        └─ «نفهمیدم» ──┐
                       ▼
             answerWithAi()  (اختیاری، فقط اگر AI_ENABLED=true)
                       │
                       ▼
              guardAnswer()  ← نگهبان عدد و طول
                       │
             ┌─────────┴─────────┐
         قبول شد            رد شد
             │                  │
      پاسخ مدل          همان سؤال روشن‌کننده‌ی قاعده‌محور
```

سه لایه در کد:

| فایل | نقش |
| --- | --- |
| `backend/src/ai/ai.service.ts` | اتصال HTTP به هر درگاه سازگار با OpenAI، تایم‌اوت، قطع‌کننده‌ی مدار |
| `backend/src/ai/context.ts` | ساخت «بسته‌ی زمینه» (تنظیمات + کاتالوگ + تاریخچه) و نگهبان خروجی |
| `backend/src/ai/answer.ts` | تنها راه فراخوانی مدل: زمینه + نگهبان، یک‌جا |

مسیرهای پنل: `GET /bot/ai` (وضعیت) و `POST /bot/preview` (پاسخ آزمایشی، همان
مسیری که مشتری می‌گیرد؛ فیلد `source` می‌گوید `rules` یا `ai`).

---

## ۲. راه‌اندازی در چهار قدم

### قدم ۱ — کلید و مدل را بگذارید

در `backend/.env` (و در Render → Environment):

```env
AI_ENABLED=true
AI_API_KEY=sk-...
AI_MODEL=gpt-4o-mini
AI_BASE_URL=https://api.openai.com/v1
```

`AI_BASE_URL` را می‌توانید عوض کنید؛ هر سرویسی که
`POST {base}/chat/completions` را با استاندارد OpenAI جواب بدهد کار می‌کند:

* `https://openrouter.ai/api/v1` (چند مدل با یک کلید)
* `https://api.groq.com/openai/v1` (سریع و ارزان)
* `http://127.0.0.1:8000/v1` (vLLM یا Ollama روی سرور خودتان — داده از کشور خارج نمی‌شود)

### قدم ۲ — سرور را دوباره بالا بیاورید

```bash
cd backend && npm run build && node dist/main.js
```

### قدم ۳ — چک کنید

```bash
# وضعیت
curl -s localhost:10000/bot/ai -H "Authorization: Bearer <TOKEN>"
# {"enabled":true,"ready":true,"model":"gpt-4o-mini","reason":""}

# پاسخ آزمایشی؛ source نشان می‌دهد مدل جواب داده یا قاعده‌ها
curl -s -X POST localhost:10000/bot/preview \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -d '{"message":"میشه بگی این مانتویی که گذاشتی چقدره؟"}'
```

### قدم ۴ — پایش

هر استفاده و هر رد شدن در دفتر گردش ثبت می‌شود:
`telegram.ai_answer` (پاسخ مدل پذیرفته شد) و `telegram.ai_skipped` (با دلیل:
`ai_disabled`، `no_answer`، `price_not_in_catalog:...`، `too_long`).

## ۳. بسته‌ی زمینه چه دارد و چرا؟

`buildFacts()` این متن را می‌سازد و همان را به مدل می‌دهد (و نگهبان با همان
مقایسه می‌کند):

```
## فروشگاه
نام: بوتیک باران
ارسال: پست پیشتاز، ۲ تا ۴ روز کاری.
پرداخت: پرداخت آنلاین یا کارت به کارت.
ساعت پاسخ‌دهی: هر روز ۹ تا ۲۳.
مرجوعی: تا ۷ روز.

## محصولات (۹ از ۱۰)
• [A1B2C3] مانتو کتان → سایز ۳۸ / رنگ کرم = ۶۴۰٬۰۰۰ تومان (۶ عدد) | سایز ۴۰ / رنگ مشکی = ۶۹۰٬۰۰۰ تومان (۲ عدد)
...
```

نکته‌های عمدی:

* **محصولات موجود اول** می‌آیند؛ اگر بودجه‌ی کاراکتر (پیش‌فرض ۵۵۰۰) تمام
  شود، محصولات ناموجود حذف می‌شوند نه قابل‌فروش‌ها.
* مدل صریح می‌بیند «۹ از ۱۰»؛ یعنی می‌داند فهرست کامل نیست و نمی‌تواند ادعای
  «همه‌ی محصولات» کند.
* تاریخچه فقط ۸ پیام آخر است (هزینه و تمرکز).
* کد محصول داخل بسته هست تا مشتری بتواند دقیق اشاره کند.

## ۴. چرا سفارش و پرداخت به مدل سپرده نمی‌شوند؟

`order-flow.ts` یک ماشین حالت است: مرحله‌ی سایز/رنگ → نام → تلفن → استان →
شهر → نشانی → کد پستی (اختیاری) → تأیید → لینک پرداخت. هر مرحله یا معتبر است
یا نیست؛ «تقریباً درست» وجود ندارد.

اگر مدل این مسیر را می‌گرفت:

1. **غیرقابل‌تکرار** می‌شد؛ یک پیام دو پالس متفاوت می‌گرفت.
2. **قابل‌حسابرسی نبود**؛ «چرا این سفارش با این آدرس ثبت شد؟» جواب نداشت.
3. **موجودی رزروشده گم می‌شد**؛ رزرو موجودی باید اتمیک باشد، نه نتیجه‌ی یک
   مکالمه‌ی آزاد.
4. **خطای پرهزینه** می‌داد؛ آدرس اشتباه یعنی مرسوله‌ی برگشتی.

جمع‌بندی: **مدل برای فهمیدن و توضیح‌دادن، ماشین حالت برای ثبت‌کردن.** این
تقسیم کار در کد رعایت شده است — مدل هیچ‌وقت در `continueOrder` صدا زده نمی‌شود.

## ۵. آزمون و امنیت

* `npm test` → `test/ai.test.ts`: ساخت زمینه، بودجه‌ی کاتالوگ، نگهبان قیمت،
  رفتار خاموش‌بودن مدل. هیچ تستی به شبکه نیاز ندارد.
* مدل بدون کلید = `enabled:false`؛ هیچ خطایی به کاربر نمی‌رسد.
* سه خطای پشت‌سرهم از ارائه‌دهنده → مدار ۲ دقیقه بسته می‌شود و بات با
  موتور قاعده‌محور ادامه می‌دهد (نه کندی، نه قطعی).
* داده‌ی حساس (توکن تلگرام، کلید درگاه) هرگز داخل پرامپت نمی‌رود؛ فقط نام و
  متن تنظیمات فروشگاه.

## ۶. کارهای بعدی (اختیاری)

1. **کلید هر فروشنده**: ستون `aiEnabled`/`aiKey` روی `Shop` و استفاده از کلید
   خود فروشنده (مدل مشترک، هزینه‌ی جدا).
2. **حافظه‌ی خلاصه**: هر ۲۰ پیام، یک خلاصه‌ی کوتاه بسازیم تا بسته‌ی زمینه
   کوچک بماند.
3. **ارزیابی**: مجموعه‌ای از ۵۰ سؤال واقعی مشتری + جواب درست، و سنجش نرخ
   پاسخ مدل در CI.
4. **حالت پیشنهاد**: مدل پاسخ را فقط «پیش‌نویس» کند و فروشنده در پنل تأیید
   کند (برای فروشگاه‌های محتاط).
