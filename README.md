# Forooshyar (فروش‌یار) — Project Plan

> دستیار هوشمند فروشگاه‌های اینستاگرامی و تلگرامی: پاسخ به دایرکت، تشخیص پست ارسالی، و همگام‌سازی زنده قیمت و موجودی از پنل فروشنده.

**نحوه استفاده:** هر تسک یک شناسه دارد (مثلاً `P1-03`). وقتی انجام شد `[ ]` را به `[x]` تبدیل کن. هر فاز یک «معیار پذیرش» دارد؛ تا برآورده نشده سراغ فاز بعد نرو.

---

## 0. اصول طراحی (تصمیم‌های ثابت)

1. **قیمت و موجودی فقط از دیتابیس می‌آید.** مدل زبانی هرگز عدد از خودش نمی‌سازد.
2. **فرش + پولیش:** سؤال‌های تکراری با بازیابی از کاتالوگ و قالب جواب داده می‌شوند (ارزان)؛ مدل زبانی فقط برای سؤال مبهم، لحن برند و تولید محتوا.
3. **یک بک‌اند، چند پلتفرم:** هر پلتفرم یک آداپتور دارد که پیام را به قالب مشترک تبدیل می‌کند.
4. **MVP روی تلگرام (و بعد بله)،** اینستاگرام کانال دوم است (به‌خاطر App Review و محدودیت دسترسی از ایران).
5. **اگر بات مطمئن نیست، ارجاع به فروشنده.** حدس‌زدن ممنوع.
6. **چندمستأجری (multi-tenant):** هر ردیف مرتبط با `shop_id` است.

## 1. استک پیشنهادی

| لایه | انتخاب |
|---|---|
| Backend | NestJS (TypeScript)، معماری ماژولار، REST API |
| Frontend (پنل فروشنده + صفحه فرود) | React با Next.js (App Router، TypeScript، RTL و فارسی‌محور) |
| DB | PostgreSQL + Prisma (+ pgvector در فاز ۳ برای جستجوی معنایی) |
| صف/کش | Redis + BullMQ |
| Worker | پردازشگرهای BullMQ داخل پروژه NestJS (پروسه جدا) |
| LLM | OpenRouter API (سازگار با OpenAI، `https://openrouter.ai/api/v1`) با کلید `OPENROUTER_API_KEY` و مدل قابل‌تنظیم `OPENROUTER_MODEL`؛ پشت لایه انتزاعی `LLMClient` |
| اعتبارسنجی | `class-validator` / `zod` |
| ساختار ریپو | مونوریپو: `apps/api` (NestJS)، `apps/web` (Next.js)، `packages/shared` (تایپ‌ها و ثابت‌های مشترک) |
| تست | Jest (واحد و e2e) در بک‌اند، Playwright یا Vitest در فرانت |
| استقرار | Docker Compose روی VPS (api، web، postgres، redis) |

## P0 — آماده‌سازی و اعتبارسنجی (هفته ۱)

**هدف:** قبل از کدنویسی سنگین، مطمئن شو مسئله واقعی است و مسیرهای فنی بسته نیستند.

- [ ] `P0-01` ساخت ریپو Private و اضافه‌کردن `README`، `.gitignore`، `.env.example`
- [ ] `P0-02` اتصال GitHub به Claude (Settings → Connectors) و تست push
- [ ] `P0-03` مصاحبه با ۱۰ تا ۱۵ صاحب فروشگاه اینستاگرامی/تلگرامی
  - سؤال‌ها: چند پیام در روز؟ پرتکرارترین سؤال‌ها؟ چقدر پول ادمین می‌دهند؟ حاضرند ماهی چقدر بدهند؟
- [ ] `P0-04` فهرست ۳۰ سؤال پرتکرار مشتری و پاسخ نمونه (برای تست)
- [ ] `P0-05` ساخت حساب OpenRouter، گرفتن API key و تست دسترسی/پرداخت/تأخیر از محیط واقعی (کلید فقط در `.env`)
- [ ] `P0-06` تست کیفیت فارسی ۲–۳ مدل از طریق OpenRouter روی ۳۰ سؤال بالا (انتخاب مدل پیش‌فرض و مدل fallback ارزان‌تر)
- [ ] `P0-07` ساخت بات تلگرام آزمایشی با BotFather و بررسی دسترسی سرور
- [ ] `P0-08` بررسی امکان ساخت اپ Meta برای اینستاگرام از شرایط فعلی (فقط بررسی، نه ساخت کامل)
- [ ] `P0-09` تصمیم نهایی نام برند، دامنه و یوزرنیم بات

**معیار پذیرش:** حداقل ۵ فروشنده گفته‌اند «اگر کار کند استفاده می‌کنم»؛ API مدل زبانی از سرور قابل‌دسترس است؛ یک مدل برای فارسی انتخاب شده.

## P1 — هسته: دیتابیس و API (هفته ۱–۲)

**هدف:** سیستم بتواند فروشگاه، محصول، واریانت و موجودی را مدیریت کند.

### ساختار پروژه
- [ ] `P1-01` مونوریپو (pnpm workspaces): `apps/api` (NestJS)، `apps/web` (Next.js)، `packages/shared`
  - ماژول‌های NestJS: `auth`, `shops`, `catalog` (products/variants), `inventory`, `channels` (adapters), `bot` (fresh/polish), `llm`, `conversations`, `posts`, `billing`, `reports`
- [ ] `P1-02` Docker Compose (api + web + postgres + redis)
- [ ] `P1-03` تنظیمات از env با `@nestjs/config` و اعتبارسنجی (zod/Joi)، لاگ ساخت‌یافته (pino)، `.env.example`
- [ ] `P1-04` Prisma: schema و migration، seed داده نمونه

### مدل داده
- [ ] `P1-05` جدول `users` (فروشنده‌ها): ایمیل/موبایل، هش رمز
- [ ] `P1-06` جدول `shops`: نام، لحن برند، قوانین ارسال، روش‌های پرداخت، ساعت کاری، پیام ارجاع
- [ ] `P1-07` جدول `channel_connections`: shop_id، پلتفرم، توکن (رمزنگاری‌شده)، وضعیت
- [ ] `P1-08` جدول `products`: shop_id، عنوان، توضیح، دسته، عکس‌ها، فعال/غیرفعال
- [ ] `P1-09` جدول `variants`: product_id، sku، سایز، رنگ، قیمت، `stock`
- [ ] `P1-10` جدول `stock_movements`: variant_id، تغییر (+/-)، دلیل (sale/restock/manual/order)، کاربر، زمان
- [ ] `P1-11` جدول‌های `conversations`، `messages`، `customers`
- [ ] `P1-12` جدول‌های `posts` و `post_product_links` (برای P5)
- [ ] `P1-13` ایندکس‌ها: `(shop_id)` روی همه، جستجوی متنی روی عنوان محصول

### منطق موجودی
- [ ] `P1-14` سرویس کم‌کردن اتمیک موجودی (داخل `prisma.$transaction`، با `updateMany`/`$executeRaw`):
  ```sql
  UPDATE variants SET stock = stock - :qty
  WHERE id = :id AND stock >= :qty;
  ```
  اگر هیچ ردیفی تغییر نکرد، یعنی ناموجود. همیشه همراه ثبت در `stock_movements` در همان تراکنش.
- [ ] `P1-15` تابع افزایش موجودی و اصلاح دستی
- [ ] `P1-16` فیلد `stock_updated_at` برای علامت‌گذاری موجودی قدیمی

### API
- [ ] `P1-17` احراز هویت (JWT با `@nestjs/jwt` و Guard) + ثبت‌نام/ورود فروشنده
- [ ] `P1-18` CRUD فروشگاه، محصول، واریانت (DTO با `class-validator`)
- [ ] `P1-19` endpoint «فروخته شد» (`POST /variants/:id/sell`)
- [ ] `P1-20` آپلود کاتالوگ از اکسل/CSV (ستون‌ها: نام، قیمت، سایز، رنگ، موجودی) + گزارش خطای هر ردیف
- [ ] `P1-21` ایزولاسیون داده: هیچ فروشگاهی نتواند داده دیگری را ببیند (Guard/Interceptor برای `shopId` + تست e2e خودکار)
- [ ] `P1-22` تست‌های Jest برای موجودی (از جمله شرایط رقابتی هم‌زمان)
- [ ] `P1-23` مستندات API با `@nestjs/swagger`، rate limit با `@nestjs/throttler`

**معیار پذیرش:** با Postman/Swagger می‌توان یک فروشگاه با ۲۰ محصول ساخت، موجودی را اتمیک کم کرد، و داده فروشگاه‌ها از هم جداست.

## P2 — بات تلگرام، فاز «فرش» (هفته ۲–۳)

**هدف:** مشتری در تلگرام می‌پرسد و جواب درست از کاتالوگ می‌گیرد، بدون LLM.

- [ ] `P2-01` قالب پیام مشترک `IncomingMessage` (platform, shop_id, customer_id, text, attachments, raw)
- [ ] `P2-02` آداپتور تلگرام: webhook (یا long polling در توسعه) → `IncomingMessage`
- [ ] `P2-03` ارسال پیام خروجی: `OutgoingMessage` → Telegram API
- [ ] `P2-04` مسیر webhook (کنترلر NestJS) با تأیید secret و پاسخ سریع `200`، پردازش در صف BullMQ
- [ ] `P2-05` شناسایی فروشگاه از روی بات/توکن (یک سرور، چند فروشگاه)
- [ ] `P2-06` ثبت اتصال بات فروشنده (وارد کردن توکن در پنل یا endpoint موقت)
- [ ] `P2-07` طبقه‌بندی قصد (Intent) با قواعد ساده:
  - `price`، `availability`، `size/color`، `shipping`، `payment`، `hours`، `greeting`، `other`
- [ ] `P2-08` نرمال‌سازی متن فارسی (ی/ک عربی، اعداد فارسی/عربی، نیم‌فاصله، حذف اعراب)
- [ ] `P2-09` جستجوی محصول از روی متن (fuzzy match روی عنوان/دسته؛ مثلاً با `fuse.js` یا full-text/`pg_trgm` پستگرس)
- [ ] `P2-10` قالب‌های جواب برای هر Intent (قابل‌تنظیم توسط فروشنده)
- [ ] `P2-11` اگر چند محصول مطابق بود: پرسیدن سؤال شفاف‌ساز با دکمه‌های انتخاب
- [ ] `P2-12` اگر هیچ محصولی پیدا نشد: پیام ارجاع به فروشنده + اعلان به فروشنده
- [ ] `P2-13` ذخیره همه گفتگوها
- [ ] `P2-14` تست روی ۳۰ سؤال نمونه (P0-04) و ثبت درصد پاسخ صحیح

**معیار پذیرش:** حداقل ۶۰٪ سؤال‌های نمونه بدون LLM درست جواب داده می‌شود و هیچ‌وقت قیمت یا موجودی اشتباه نمی‌گوید.

## P3 — لایه «پولیش» با LLM و ارجاع به انسان (هفته ۳–۴)

**هدف:** جواب طبیعی، هماهنگ با لحن برند، و امن.

- [ ] `P3-01` ماژول `llm` در NestJS: اینترفیس `LLMClient` با پیاده‌سازی `OpenRouterClient` (endpoint سازگار با OpenAI: `https://openrouter.ai/api/v1/chat/completions`، کلید از `OPENROUTER_API_KEY`، مدل از `OPENROUTER_MODEL`؛ قابل جایگزینی با ارائه‌دهنده دیگر)
- [ ] `P3-02` مدیریت خطا: timeout، retry با backoff، مدل fallback (`OPENROUTER_FALLBACK_MODEL`) و در نهایت fallback به قالب فرش
- [ ] `P3-03` ساخت پرامپت: لحن برند + قوانین فروشگاه + **فقط** داده‌های بازیابی‌شده از DB (قیمت/موجودی به‌صورت JSON ثابت داخل پرامپت)
- [ ] `P3-04` قانون سخت در پرامپت: «عدد، قیمت، موجودی و تخفیف جز از داده ورودی نگو؛ اگر نمی‌دانی ارجاع بده»
- [ ] `P3-05` اعتبارسنجی خروجی (Guardrail): هر عددی که در جواب هست باید در داده ورودی باشد، وگرنه جواب رد و به قالب فرش/ارجاع برمی‌گردد
- [ ] `P3-06` مسیریابی: فرش اگر مطمئن؛ پولیش اگر سؤال مبهم یا نیاز به لحن
- [ ] `P3-07` تشخیص شرایط ارجاع به انسان: مشتری عصبانی، شکایت، مرجوعی، تخفیف، سؤال خارج از کاتالوگ، درخواست مستقیم انسان
- [ ] `P3-08` اعلان به فروشنده (تلگرام) با خلاصه گفتگو و لینک پاسخ
- [ ] `P3-09` حالت «بات خاموش برای این مشتری» وقتی فروشنده وارد گفتگو شد
- [ ] `P3-10` حافظه گفتگو: چند پیام آخر + محصول مورد بحث
- [ ] `P3-11` ثبت هزینه (توکن) هر پیام و سقف روزانه به‌ازای هر فروشگاه
- [ ] `P3-12` مجموعه تست ارزیابی (eval) ۵۰ سؤال: صحت قیمت، صحت موجودی، رفتار ارجاع
- [ ] `P3-13` محافظت در برابر Prompt Injection (پیام مشتری هرگز دستور سیستم نیست)

**معیار پذیرش:** در eval، صفر خطای قیمت/موجودی؛ ارجاع صحیح در موارد حساس؛ هزینه متوسط هر پیام اندازه‌گیری شده.

## P4 — پنل فروشنده (هفته ۳–۵)

**هدف:** فروشنده بدون کمک شما بتواند همه‌چیز را مدیریت کند. این مهم‌ترین ریسک محصول است: «زحمت پر کردن کاتالوگ» باید حداقل باشد.

- [ ] `P4-00` راه‌اندازی `apps/web` (Next.js App Router + TypeScript)، RTL سراسری، فونت فارسی، کتابخانه UI (مثلاً Tailwind + shadcn/ui)، کلاینت API تایپ‌شده از `packages/shared` (یا OpenAPI)، مدیریت احراز هویت (کوکی httpOnly)
- [ ] `P4-01` ثبت‌نام/ورود/بازیابی رمز
- [ ] `P4-02` ویزارد راه‌اندازی (Onboarding): نام فروشگاه → اتصال بات → افزودن اولین محصول → تست جواب
- [ ] `P4-03` لیست محصولات با جستجو و فیلتر
- [ ] `P4-04` فرم افزودن/ویرایش محصول با واریانت‌ها
- [ ] `P4-05` آپلود اکسل و پیش‌نمایش قبل از ثبت
- [ ] `P4-06` **دکمه سریع «فروخته شد»** و ویرایش سریع موجودی/قیمت (حالت موبایل‌محور)
- [ ] `P4-07` علامت «موجودی قدیمی» و یادآوری به‌روزرسانی
- [ ] `P4-08` تنظیمات فروشگاه: لحن، ارسال، پرداخت، ساعت کاری، پیام ارجاع
- [ ] `P4-09` مشاهده گفتگوها + امکان پاسخ دستی
- [ ] `P4-10` صندوق «نیاز به پاسخ شما» (موارد ارجاع‌شده)
- [ ] `P4-11` پیش‌نمایش «بات چه جوابی می‌دهد» (چت آزمایشی داخل پنل)
- [ ] `P4-12` طراحی ریسپانسیو (فروشنده‌ها بیشتر با موبایل کار می‌کنند)
- [ ] `P4-13` فارسی‌سازی و راست‌چین کامل

**معیار پذیرش:** یک فروشنده غیرفنی در کمتر از ۱۵ دقیقه فروشگاهش را راه می‌اندازد و اولین جواب خودکار را می‌گیرد.

## P5 — تشخیص پست ارسالی (هفته ۵)

**هدف:** مشتری پست را فوروارد/اشتراک می‌کند و قیمت می‌پرسد؛ بات محصول را می‌شناسد.

**اصل:** تطبیق مستقیم با شناسه/لینک پست، نه تشخیص تصویر.

- [ ] `P5-01` تلگرام: استخراج شناسه کانال و پست از پیام فورواردشده و ثبت در `posts`
- [ ] `P5-02` همگام‌سازی پست‌های کانال فروشگاه (از طریق پست‌های جدیدی که بات می‌بیند، با افزودن بات به کانال)
- [ ] `P5-03` در پنل: وصل‌کردن هر پست به یک/چند محصول یا واریانت
- [ ] `P5-04` تطبیق: پیام فورواردشده → پست → محصول → جواب با قیمت/موجودی لحظه‌ای
- [ ] `P5-05` **پیش‌نویس خودکار از کپشن:** استخراج نام، قیمت، سایزها از کپشن (قواعد + LLM) و ارائه به فروشنده برای تأیید یک‌کلیکی
- [ ] `P5-06` پست وصل‌نشده: پیشنهاد نزدیک‌ترین محصول از روی کپشن؛ اگر مطمئن نبود ارجاع
- [ ] `P5-07` (بعداً، اولویت پایین) اسکرین‌شات/عکس: تشخیص با embedding تصویر
- [ ] `P5-08` تست: ۲۰ پست نمونه با نرخ تطبیق صحیح بالای ۹۵٪ برای پست‌های وصل‌شده

**معیار پذیرش:** پست فوروارد شده ← محصول درست با قیمت و موجودی درست.

> وقتی اینستاگرام اضافه شد (P7)، همین منطق با shortcode پست و Graph API جزئیات پیاده می‌شود. ساختار payload را از مستندات فعلی Meta چک کن.

## P6 — بتای واقعی (هفته ۶)

**هدف:** اثبات ارزش با کاربر واقعی.

- [ ] `P6-01` استقرار روی VPS (HTTPS، دامنه، ریستارت خودکار، بکاپ روزانه DB)
- [ ] `P6-02` مانیتورینگ و هشدار خطا (Sentry یا مشابه) + لاگ
- [ ] `P6-03` جذب ۵ تا ۱۰ فروشگاه بتا (از مصاحبه‌های P0)

## 5. ریسک‌ها و راه‌حل‌ها

| ریسک | راه‌حل |
|---|---|
| فروشنده کاتالوگ را پر نمی‌کند | ویزارد ساده، آپلود اکسل، پیش‌نویس خودکار از کپشن، دکمه سریع «فروخته شد» |
| موجودی قدیمی و جواب اشتباه | علامت قدیمی بودن، لحن محتاط («با فروشنده هماهنگ می‌کنم»)، یادآوری |
| بات قیمت اشتباه می‌گوید | قیمت فقط از DB، Guardrail خروجی (P3-05)، تست eval |
| محدودیت/مسدودی اینستاگرام | شروع با تلگرام/بله؛ اینستاگرام فقط رسمی (API) |
| دسترسی و پرداخت OpenRouter از ایران | تست در P0-05، سرور/پراکسی خارج از ایران در صورت نیاز، لایه انتزاعی `LLMClient`، امکان تغییر مدل/ارائه‌دهنده با env |
| هزینه LLM | فرش اول، سقف روزانه، ثبت هزینه هر پیام |
| رقابت | تمرکز روی فارسی، لحن، قیمت و پشتیبانی نزدیک |
| ریزش مشتری | گزارش ارزش هفتگی، پشتیبانی شخصی در بتا |
| امنیت توکن‌ها | رمزنگاری در DB، `.env` خارج از گیت، revoke در صورت لو رفتن |
| حریم خصوصی | حداقل داده، سیاست حریم خصوصی، امکان حذف داده مشتری |
